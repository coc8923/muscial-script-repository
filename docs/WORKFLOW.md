# 공동작업 규칙

> 두 사람이 각자 다른 컴퓨터에서 같은 대본을 작업하기 위한 약속입니다.
> 규칙은 적을수록 좋습니다. 그래서 **꼭 필요한 것만** 남겼습니다.

---

## 🥇 황금 규칙

```
작업 시작 전 → Pull  (받기)
작업 끝난 후 → Push  (올리기)
```

사고의 90%는 이 둘 중 하나를 빼먹어서 생깁니다.
**특히 Pull을 빼먹는 것이 가장 위험합니다.**

왜냐하면 Push를 빼먹으면 "상대방이 내 작업을 못 보는" 정도로 끝나지만,
Pull을 빼먹으면 **상대방이 고친 내용 위에 내 옛날 내용을 덮어쓰게 되어** 충돌이 납니다.

---

## 📐 규칙 1 — 영역을 나눈다

같은 파일을 동시에 건드리지 않는 것이 **충돌을 막는 유일한 확실한 방법**입니다.

작업 시작 전에 한 줄만 주고받으세요.

> "오늘 나는 3장이랑 4장 볼게"
> "그럼 나는 인물 설정 손볼게"

### 왜 이게 중요한가요?

프로그램 코드는 충돌이 나도 기계가 어느 정도 자동으로 합쳐줍니다.
그런데 **대본은 다릅니다.**

| 상황 | 기계의 판단 |
|---|---|
| 서로 **다른 줄**을 고침 | ✅ 자동으로 합쳐짐 |
| 서로 **같은 줄**을 고침 | ❌ 기계가 판단 불가 → 사람이 해결 |

"이 대사가 더 좋은가?"는 기계가 절대 판단할 수 없습니다.
결국 두 사람이 앉아서 한 줄씩 비교해야 합니다. 이게 공동 대본작업의 진짜 고통입니다.

---

## 📁 규칙 2 — 파일을 잘게 나눈다

**한 파일에 전체 대본을 몰아넣지 않습니다.** 장면 하나당 파일 하나.

```
❌ 나쁜 예              ✅ 좋은 예
Script/                Script/
  └─ 대본전체.md          ├─ 01-prologue.md
                          ├─ 02-paris-morning.md
                          └─ 03-first-meeting.md
```

파일이 나뉘어 있으면 서로 다른 장면을 동시에 작업해도 **충돌이 아예 나지 않습니다.**

---

## 🔤 규칙 3 — 파일 이름은 영문·숫자로

파일 **이름**은 영문 소문자와 숫자, 하이픈(`-`)만 씁니다.
한글 제목은 파일 **안에** 첫 줄로 씁니다.

```
파일 이름:  03-first-meeting.md
파일 첫 줄: # 3장 — 첫 만남
```

### 왜요?

맥과 윈도우는 한글 파일 이름을 **내부적으로 다르게 저장**합니다.
맥은 NFD(풀어쓰기), 윈도우는 NFC(모아쓰기) 방식입니다.

요즘 Git은 맥에서 이걸 자동으로 맞춰줍니다(`core.precomposeunicode` 기본값 `true`).
그래서 대부분은 문제없이 돌아갑니다. **다만 한번 어긋나면** 같은 파일이 두 개로
보이거나 사라진 것처럼 보이고, 고치려면 파일을 지웠다가 다시 넣어야 합니다.

굳이 그 위험을 감수할 이유가 없으니, 처음부터 영문으로 쓰는 습관을 권합니다.

> 참고: [Git & Mac: Working with Unicode filenames](https://makandracards.com/makandra/17827-git-mac-working-unicode-filenames)

**맥에서 설정 확인하는 법** (터미널에 입력):
```bash
git config --get core.precomposeunicode
```
`true`가 나오면 정상입니다. 아무것도 안 나오면 아래를 실행하세요:
```bash
git config --global core.precomposeunicode true
```

## ✍️ 규칙 4 — 커밋 메시지는 "뭘 했는지" 한 줄

커밋(Commit)은 **작업 기록을 남기는 것**입니다. 나중에 "언제 뭐가 바뀌었지?"를
찾을 때 이 한 줄이 전부입니다.

| ❌ 이렇게 쓰지 마세요 | ✅ 이렇게 쓰세요 |
|---|---|
| `수정` | `3장 앙투안 첫 대사 짧게 줄임` |
| `ㅇㅇ` | `마리 인물 설정에 두려움 항목 추가` |
| `asdf` | `1942년 파리 통행금지 시각 조사 기록` |

**요령**: "무엇을" + "어떻게 했다" 로 씁니다. 이유까지 쓰면 더 좋습니다.

## 🔥 규칙 5 — 충돌이 나면 혼자 해결하지 않는다

`conflict`라는 빨간 글자가 뜨면 **멈추세요.**

1. 상대방에게 연락합니다 (전화가 제일 빠릅니다)
2. 어느 파일이 충돌했는지 확인합니다
3. **두 사람이 같이** 어느 쪽 문장을 살릴지 정합니다
4. 정한 대로 고치고 다시 Commit → Push

> 💡 Claude에게 이렇게 물어보면 도와줍니다:
> `충돌 난 파일 보여주고, 양쪽이 뭘 다르게 썼는지 설명해줘`
>
> 단, **어느 쪽 대사가 좋은지는 Claude가 정하게 두지 마세요.** 그건 작가의 몫입니다.

## 🚫 절대 하지 말 것

| 하지 말 것 | 왜 |
|---|---|
| 상대방이 작업 중인 파일 건드리기 | 확실한 충돌 |
| Pull 안 하고 작업 시작 | 가장 흔한 사고 원인 |
| 며칠치 작업을 한 번에 Push | 충돌 범위가 눈덩이처럼 커짐 |
| 커밋 메시지에 `수정`, `ㅇㅇ` | 나중에 아무도 못 찾음 |
| Claude 계정 하나를 둘이 공유 | 사용량 한도 반토막 + 정책 위반 |
| 남의 가사·대본 통째로 붙여넣기 | 저작권. 이 저장소는 공개일 수 있음 |

## 🌿 (선택) 큰 작업은 브랜치에서

**"1막 전체를 갈아엎겠다"** 같은 큰 작업을 할 때만 쓰세요.
일상적인 수정에는 필요 없습니다.

브랜치(branch)는 **원본을 건드리지 않고 따로 작업하는 복사본**입니다.
망해도 원본은 멀쩡합니다.

Claude에게 이렇게 말하면 됩니다:
```
act1-rewrite 라는 브랜치 만들어줘
```

작업이 끝나고 마음에 들면:
```
이 브랜치를 main에 합쳐줘
```

마음에 안 들면 그냥 버리면 됩니다. **원본(main)은 그대로입니다.**

## 📞 하루 흐름 예시

```
09:00  [카톡]  "오늘 나는 3~4장 볼게"
       [카톡]  "ㅇㅋ 나는 인물설정 손볼게"
              ↓
09:05  GitHub Desktop → Fetch/Pull  ← 반드시 먼저!
              ↓
09:10  터미널 → claude → 작업
              ↓
12:00  GitHub Desktop → Commit ("3장 앙투안 대사 다듬음") → Push
              ↓
12:05  [카톡]  "3장 올렸어, 봐줘"
```
